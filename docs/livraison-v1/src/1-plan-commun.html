3. Pourquoi ce périmètre

  • Les P1 d'abord. docs/11-anomalies-connues.md classe P1 ce qui doit être corrigé « avant toute ouverture à des utilisateurs réels ». La V1 ouvre l'outil : P1-06 (#5) et P1-08 (#1) en font partie et sont prêts.
  • Petit et réversible. Tout ce qui part en V1 est sans migration et sans script de données : chaque fusion peut être annulée par un simple git revert, sans toucher la base.
  • La pile A3/A4 est structurante. Fonctions SQL SECURITY DEFINER, droits PostgreSQL, verrous transactionnels, registre d'idempotence : la relire sérieusement demande 3 à 5 jours, et une migration ratée en production la veille d'une livraison serait le pire scénario. Elle mérite une fenêtre dédiée, avec sauvegarde et script de vérification préalable (déjà écrit par Aya : scripts/a43-preflight-readonly.sql).
  • #2 est conditionnel parce qu'il modifie ce que la collecte accepte. Il corrige un vrai problème métier (vieilles vidéos réindexées présentées comme nouvelles), mais un réglage trop strict viderait la veille. Il ne part que si le test de collecte comparatif est bon (section 12).

4. Les règles de la semaine

  1. Périmètre figé. Seules les PR de la section 2 marquées V1 ou conditionnelles peuvent entrer dans main. Toute autre idée va dans une note « V1.1 ».
  2. Aucune migration SQL et aucun script db/data/ ne doivent entrer dans main cette semaine.
  3. Pas de fusion sans CI verte et sans relecture. Les PR d'Anne-Laure sont relues par Aya. Les PR d'Aya sont relues par Anne-Laure (exercice de formation) et la décision finale revient à Amine pour #2 et #3.
  4. On ne réécrit pas l'historique publié. Pas de git push --force, pas de rebase, commit --amend ou squash sur des commits déjà poussés. Pour se mettre à jour : git merge origin/main --no-edit (sans --no-edit, Git ouvre un éditeur de texte dans le terminal). Si GitHub propose « Update branch », choisir « Update with merge commit », jamais « Update with rebase ».
  5. Fusion sur GitHub avec « Create a merge commit », jamais « Squash » ni « Rebase ». GitHub mémorise le dernier choix : le vérifier à chaque fusion.
  6. Une PR = un sujet. Aucun reformatage de fichiers hors sujet. Les fichiers de src/integrations/ sont générés par la plateforme : on ne les modifie jamais à la main.
  7. Après chaque fusion dans main, les branches encore ouvertes font git merge origin/main --no-edit et repassent la CI avant leur relecture.
  8. Gel du code mercredi 18 h. Ensuite, seul un correctif bloquant validé par Amine peut entrer, par une PR courte relue par l'autre ingénieure.
  9. Aucun secret dans le dépôt. AI_API_KEY, SUPABASE_SERVICE_ROLE_KEY, LOVABLE_API_KEY, PERPLEXITY_API_KEY, LINKEDIN_APP_USER_CONNECTOR_CLIENT_API_KEY, APP_USER_CONNECTION_KEY_SECRET et WORDPRESS_APP_PASSWORD restent dans les paramètres du projet sur la plateforme. Le fichier .env versionné ne contient que des valeurs publiques.
  10. Messages de commit et descriptions de PR en français, qui disent ce qui change et pourquoi. Aucune mention d'outil de génération de code dans les commits, les PR, le code ou la documentation (le contrôle n° 5 le vérifie).
  11. Les PR #4, #6 et #7 ne sont ni fusionnées ni rebasées, et leur branche de base ne change pas cette semaine.
  12. Aucune modification dans l'éditeur de la plateforme cette semaine. Une modification faite dans l'éditeur arrive directement sur main, sans PR, sans relecture et sans CI. Tout passe par GitHub.
  13. On nomme les fichiers qu'on valide : git add <fichier>, jamais git add -A, git add . ni git commit -a. Avant chaque commit, git status : si .env apparaît comme modifié, git restore .env et prévenir Aya. Ce fichier est versionné ; une clé ajoutée dedans pour un essai serait publiée.
  14. En local, toujours SUPABASE_URL= bun run dev, avec le SUPABASE_URL= vide devant. Le .env versionné contient l'adresse de la base de production : un simple bun run dev s'y connecterait. Après chaque démarrage, vérifier le mode (section 9) ; tout autre résultat que {"mode":"demo"} : arrêter le serveur immédiatement.

7. Cycle de vie d'une PR (définition de « terminé »)

Une PR est prête à être relue quand toutes les cases sont cochées :

  • La branche contient origin/main à jour (git merge origin/main --no-edit, jamais de rebase).
  • git diff origin/main --stat ne montre que des fichiers liés au sujet de la PR.
  • Aucun fichier de src/integrations/ n'apparaît dans le diff.
  • Les cinq contrôles passent en local (bloc ci-dessous).
  • Un test qui échouait avant le correctif et passe après est présent.
  • docs/11-anomalies-connues.md est à jour : une anomalie corrigée sort des tableaux et entre dans « Corrigées depuis la consolidation » ; une anomalie partiellement corrigée ne décrit plus que ce qui reste vrai.
  • La description de la PR suit le modèle : problème, changement, tests, limites, comment vérifier.
  • La CI GitHub est verte.

Une fois par poste, avant toute commande de ces documents : echo 'setopt interactivecomments' >> ~/.zshrc && source ~/.zshrc. Sans ce réglage, le zsh de macOS passe les commentaires de fin de ligne (# …) à la commande, qui échoue.

# Les cinq contrôles, depuis la racine du dépôt (Node 24, bun 1.2.19), branche à jour avec main
git fetch origin
bun install --frozen-lockfile
bunx tsc --noEmit -p .              # 1. TypeScript : aucune erreur
bun run lint                        # 2. 0 erreur ; les 6 avertissements react-refresh sont connus
bun --no-env-file run test          # 3. tous les tests verts
bun --no-env-file run build         # 4. build OK
# 5. Hygiène du diff : chacune des quatre commandes suivantes ne doit RIEN afficher
git diff --check origin/main
git diff origin/main --name-only | grep -E '^(\.env|drizzle/|db/|supabase/|src/integrations/)'
git diff origin/main | grep '^+' | grep -i -E 'cursor|grok|chatgpt|claude|codex|copilot|gemini'
git log origin/main..HEAD --format=%B | grep -i -E 'cursor|grok|chatgpt|claude|codex|copilot|gemini|co-authored'

Le contrôle 5 attrape ce que les tests ne voient pas : une espace en fin de ligne ou un marqueur de conflit oublié (<<<<<<<) dans un document, un fichier interdit (.env, migration, script de données, fichier généré), une mention d'outil de génération de code. S'il affiche quoi que ce soit, on corrige avant de pousser. Vérifié le 8 novembre : sur les branches actuelles, il signale exactement les défauts connus (fichiers générés de #5 et #1, mentions d'outils de #2), et plus rien une fois les procédures appliquées.

9. Tester une collecte réelle en local, sans toucher la production

En local, sans SUPABASE_URL, l'application tourne sur un dépôt en mémoire (mode démonstration) mais utilise le vrai collecteur (RealCollector) : elle lit les vrais flux RSS et Google News. Sans AI_API_KEY ni clés Perplexity dans le terminal, aucun appel payant n'est fait (textes par gabarits, Perplexity « non configuré »). C'est le bon terrain pour comparer main et une branche.

Le test est automatisé par le script test-collecte.sh, joint à ces documents. Il a été vérifié le 8 novembre sur main et sur la version finale de la semaine. Il refuse de s'exécuter si l'application n'est pas en mode démonstration : il ne peut pas écrire dans la base de production. Il fait, sans clic manuel : ajout des 8 entreprises du jeu de contrôle et de leur source « Site officiel » (la source Google News est créée automatiquement), collecte de chacune des 16 sources, essai de deux adresses dangereuses, tableau des résultats. Durée : environ 15 secondes par passage.

# Une seule fois : ranger le script hors du dépôt
mkdir -p ~/kora-tests && cp test-collecte.sh ~/kora-tests/

# Terminal 1 : lancer l'application sur la branche à tester
git fetch origin && git switch <branche> && git pull --ff-only
bun install --frozen-lockfile
unset AI_API_KEY PERPLEXITY_API_KEY LOVABLE_API_KEY
SUPABASE_URL= bun run dev --port 5199     # le SUPABASE_URL= vide est indispensable

# Terminal 2 : contrôle de sécurité, puis le test
curl -s http://localhost:5199/api/auth/config   # doit afficher exactement {"mode":"demo"}, sinon Ctrl+C dans le terminal 1
bash ~/kora-tests/test-collecte.sh 5199

Protocole comparatif (30 minutes, en binôme)

  1. Sur main : lancer l'application, puis le script. Il affiche un tableau et l'enregistre dans ~/kora-tests/ (jamais dans le dépôt).
  2. Arrêter le serveur (Ctrl+C dans le terminal 1). Le dépôt en mémoire repart à zéro : un seul passage du script par démarrage.
  3. Passer sur la branche testée (git switch <branche>, bun install --frozen-lockfile), relancer l'application, vérifier le mode, relancer le script.
  4. Faire les deux passages à quelques minutes d'intervalle : les flux évoluent dans la journée, une nouvelle publication entre deux passages fausserait la comparaison.
  5. Coller les deux tableaux dans la PR, avec une phrase de conclusion par critère ci-dessous.

Retour arrière

Rien de ce qui part en V1 ne touche la base : revenir en arrière ne demande qu'un commit d'annulation.

# Annuler une PR fusionnée, sans réécrire l'historique
git fetch origin && git switch -c revert/<sujet> origin/main
git log --oneline --first-parent -10     # repérer « Merge pull request #N » de la PR à annuler
git revert -m 1 --no-edit <sha-du-commit-de-fusion>
# les cinq contrôles, push, PR « Annulation de #N : raison », fusion, puis republier

-m 1 est obligatoire pour annuler un commit de fusion : il indique de revenir à l'état de main avant la fusion. Pour annuler plusieurs PR, les annuler de la plus récente à la plus ancienne, une par une. Vérifié sur la simulation : l'annulation seule de #2, de #3 ou de #1 passe sans conflit (avec #1 annulée : TypeScript OK, 678 tests verts). L'annulation de #5 crée un conflit dans docs/11, car les PR suivantes ont écrit à côté : dans ce cas, appeler Aya plutôt que forcer.

En cas d'urgence absolue (production inutilisable), republier la version précédente depuis l'historique de publication de la plateforme si elle le permet, puis faire le revert ci-dessus pour remettre main en cohérence.
