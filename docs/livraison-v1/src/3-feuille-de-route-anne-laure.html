2. Avant de commencer (lundi, 15 minutes)

2.1 Pourquoi tes CI étaient rouges

Ce n'était pas ton code. Sur main, ESLint échoue sur des fichiers régénérés automatiquement par la plateforme (src/integrations/supabase/*, src/integrations/lovable/appUserConnector.ts). Pour avoir une CI verte, tu les as reformatés dans chaque branche : c'était logique, mais ces fichiers sont réécrits par la plateforme à chaque synchronisation, et ce reformatage crée du bruit et des conflits. Lundi matin, la PR 0 d'Aya règle le problème une fois pour toutes sur main. Ensuite, tes branches doivent revenir à la version de main pour tous les fichiers qui ne concernent pas leur sujet.

2.2 Les règles qui comptent pour toi cette semaine

  • Mettre une branche à jour = git fetch origin puis git merge origin/main --no-edit. Jamais git rebase, jamais git push --force, jamais git commit --amend sur un commit déjà poussé. (Sans --no-edit, Git ouvre un éditeur dans le terminal pour le message. Si ça arrive, accepte le message proposé : dans vim, tape :wq puis Entrée ; dans nano, Ctrl+X.)
  • Si Git annonce un conflit qui n'est pas prévu dans ce document : git merge --abort (rien n'est perdu) et appelle Aya. Les conflits prévus sont tous décrits ici, avec leur résolution exacte.
  • Tu nommes toujours les fichiers que tu valides : git add <fichier>. Jamais git add -A, git add . ni git commit -a. Avant chaque commit : git status. Si .env y apparaît, git restore .env et préviens Aya : ce fichier est versionné, et une clé ajoutée dedans serait publiée sur GitHub.
  • En local, toujours SUPABASE_URL= bun run dev, jamais bun run dev seul : le .env contient l'adresse de la base de production.
  • Rien dans l'éditeur de la plateforme cette semaine : tout passe par une branche et une PR.
  • Une PR ne contient que son sujet. Pas de reformatage d'autres fichiers, pas de changement de version de dépendance, pas de fichier de src/integrations/.
  • Ne jamais supprimer un test qui gêne : comprendre pourquoi il échoue, puis corriger le code ou l'attendu, et l'expliquer dans le commit. (Tu l'as très bien fait le 6 novembre en rétablissant ton test.)
  • Garde ta méthode : test rouge, correction minimale, test vert, un commit par étape. C'est exactement ce qu'on attend.
  • Messages de commit en français, qui disent ce qui change et pourquoi, sans fautes de frappe (relis avant de valider). Aucune mention d'outil de génération de code.
